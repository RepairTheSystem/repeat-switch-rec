# Одностадийная рекомендательная модель с режимом повторов

## Идея

Одностадийные генеративные модели заменяют весь каскад (кандидаты → ранжирование) одной моделью.
В музыке повтор — главный позитивный сигнал. На маркетплейсе есть два разных режима:

- **расходники** (корм, вода) — нужно повторять, причём вовремя;
- **товары длительного пользования** (холодильник) — повторять нельзя.

**Гипотеза:** одностадийной модели на маркетплейсе нужен выученный переключатель «повтор / новое» на каждый запрос,
и он лучше, чем фиксированная квота повторов в выдаче.

Архитектурно модель — SASRec-подобный трансформер + механизм RepeatNet (Ren et al., AAAI 2019):
repeat-голова (pointer на историю) + explore-голова (softmax по каталогу без истории) + переключатель.

## Варианты

Все правила смешивания (`mixing.py`) применяются к одним и тем же двум головам — эвристическим (`heur/…`)
или нейросетевым (`nn/…`), так что эффект правила изолирован.

| Вариант          | Что делает |
|------------------|------------|
| `pop`            | популярность за 30 дней (нижняя граница) |
| `freq+pop`       | товары из истории по частоте покупок, остаток — популярное |
| `tifu-knn`       | упрощённый TIFU-KNN: вектор покупок с затуханием + соседи; гиперпараметры подбираются на val |
| `*/base`         | одна шкала без режимов (`nn/base` — отдельно обученная модель с одной головой) |
| `*/fixed30`      | жёстко 3 слота из repeat-головы + 7 из explore (как в первой версии) |
| `*/fixed-tuned`  | квота q подобрана на val — **честная** версия гипотезы «фиксированная квота» |
| `*/switch`       | мягкая смесь `p·P_repeat + (1−p)·P_explore`, `p` — выученный переключатель |
| `*/route`        | жёсткий роутинг: `p > thr` → вся выдача из repeat-головы, иначе — из explore (порог на val) |
| `*/oracle-switch`, `*/oracle-quota` | переключатель/квота знают истинную долю повторов в целях — **верхняя граница** выигрыша от любого переключателя |

Repeat-голова видит «возраст» каждой покупки на момент запроса (лог-корзины по времени),
поэтому может выучить, что воду три дня назад покупать рано.

**Абляция switch-модели** (`--switch-variants`, префикс в отчёте — `nn+<вариант>/…`):

| вариант | что меняется |
|---------|--------------|
| `switch` (`nn/…`) | исходная модель |
| `mask`  | explore-голова исключает **всю** историю пользователя, а не только окно последних `max_len=50` покупок — на обучении и на инференсе |
| `mask+bias`  | + обучаемая «повторяемость» каждого товара в логите указателя |
| `mask+null`  | + пустой слот указателя: если повторять нечего, масса уходит в explore |
| `mask+prior` | + сглаженная доля повторных покупок товара по train (счётчик) с обучаемым весом |
| `mask+all`   | всё вместе |

## Методология

**Данные — синтетика с известной правдой** (`data.make_synthetic`), три режима по доле повторов среди целей:

| режим  | `consumable_share` | `durable_rate` | доля повторов среди целей |
|--------|--------------------|----------------|---------------------------|
| `high` | 0.40               | 0.5            | 0.82–0.88 (исходная синтетика) |
| `mid`  | 0.15               | 15             | 0.23–0.54 |
| `low`  | 0.10               | 15             | 0.13–0.37 |

Шум, чтобы данные не повторяли устройство модели один в один: смена любимого бренда (`brand_switch`),
паузы-отпуска, после которых расходник покупается «не по графику» (`pause_prob`), сезонные категории (`seasonal_share`).

**Протокол** (`data.make_protocol`):

- модель учится на событиях `< t_val` (день 351); val-окно `[351, 358)` — ранняя остановка и подбор
  квоты, порога роутинга и гиперпараметров TIFU-KNN; test-окно `[358, 365)` — только отчёт;
- на тесте модель не переобучается, но история пользователя дополняется событиями до 358;
- **запрос — в начале окна, цели — все различные товары, купленные в окне.**
  В первой версии время запроса = точное время целевой покупки — это утечка (модель знает, когда человек купит).
  Старый протокол оставлен как `--protocol next`, а `--protocol next-start` — та же одна цель без утечки;
  разница между ними и есть цена утечки;
- 3 сида (сид меняет и данные, и инициализацию), парный бутстрап по пользователям (95% CI).

**Метрики** (`metrics.py`):

- Recall@10, NDCG@10, HR@10 — с несколькими целями на пользователя;
- **Recall отдельно по repeat- и explore-целям** (микро-усреднение по целям): общая метрика прячет провал на одной из частей;
- `repeat slots` — доля выдачи, занятая повторами; `wasted slots` — слоты на уже купленные товары длительного пользования;
- качество переключателя: `switch AUC` (различает ли запросы, где больше половины целей — повторы)
  и `switch Brier` (калибровка `p` относительно истинной доли повторов).

## Файлы

- `data.py` — синтетика с регуляторами и шумом, протоколы оценки, загрузчик T-ECD (сейчас не используется)
- `metrics.py` — метрики с разбивкой repeat/explore, AUC/Brier переключателя, парный бутстрап
- `mixing.py` — правила смешивания голов (quota / switch / route) и подбор параметров на val
- `baselines.py` — pop, freq+pop, TIFU-KNN
- `heuristics.py` — эвристические repeat/explore-головы
- `model.py` — трансформер + repeat-голова (pointer) + explore-голова + переключатель
- `train.py` — весь эксперимент: свип по режимам и сидам, абляция, латентность; отчёт в `results/<out>/summary.md` (+ CSV)
- `latency_bench.py` — латентность без обучения (веса на задержку не влияют): batch и online p50/p95/p99
- `lr_probe.py` — подбор learning rate на val
- `kaggle/build_notebook.py` → `kaggle/repeat_switch_kaggle.ipynb` — самодостаточный ноутбук для GPU

## Запуск

```bash
pip install torch numpy pandas tabulate
python train.py                                             # 3 режима × 3 сида, ~1–1.5 ч на CPU
python train.py --regimes high --seeds 0 --out results/quick  # один прогон, ~8 мин
python train.py --skip-nn                                   # только бейзлайны и эвристики, ~3 мин
python train.py --protocol next --regimes high --out results/leak_next
python train.py --protocol next-start --regimes high --out results/leak_next_start
python train.py --switch-variants switch mask mask+all     # абляция не целиком
python latency_bench.py --device cpu                       # латентность, ~2 мин
```

lr подобраны на val (`python -u lr_probe.py`): `--lr-base 1e-3 --lr-switch 3e-3`. Передавай их явно.

### Выводы

- **Гипотеза подтверждается на синтетике.** `nn/switch` лучше *лучшей подобранной* фиксированной квоты
  во всех 9 прогонах, интервал везде выше нуля. Выигрыш +0.006…+0.014 при 82–88% повторов и
  +0.019…+0.037 при 13–54%.
- **Переключатель забирает бо́льшую часть возможного:** до оракула (знает истинную долю повторов) остаётся 0.008–0.036.
- **Мягкая смесь лучше жёсткого роутинга** на 0.013–0.126; в mid/low роутинг хуже даже подобранной квоты.
  Вариант «классификатор запроса → отдельная модель» проигрывает: запросы, где часть целей — повторы,
  а часть — новое, жёсткий роутинг обслуживает плохо.
- **Explore:** в mid/low Recall по explore-целям у `nn/switch` вдвое выше, чем у `nn/base` (0.31 против 0.16, 0.33 против 0.18).
  В high — немного ниже (0.15 против 0.17): там переключатель почти всё отдаёт повторам. (В предварительной версии
  README было написано «не проседает во всех режимах» — для high это было неверно уже на сиде 0.)
- **Простые правила сильны только там, где почти всё — повторы:** `freq+pop` отстаёт от `nn/switch` на 0.03 в high,
  но в mid/low падает до 0.22–0.35, потому что вообще не рекомендует новое.
- **Слабое место нейросети — `wasted slots`:** в mid/low `nn/switch` тратит ~2 слота из 10 на уже купленные
  товары длительного пользования (у `nn/base` — 4–5, у эвристик — 0). Причина оказалась не в repeat-голове,
  а в окне истории — см. ниже.
- **Утечка времени запроса на этой синтетике ничего не стоит:** `next` − `next-start` в среднем от −0.005 до +0.007
  по вариантам, по сидам в пределах ±0.02 без знака. Протокол `window` оставлен как корректный, но старые цифры
  утечкой завышены не были.

### Ограничения

- **Режимы нестабильны по доле повторов:** в mid она 0.23–0.54, в low — 0.13–0.37 в зависимости от сида,
  потому что число расходных категорий случайное (Бернулли на каждую категорию). Агрегат «по режиму» смешивает
  разные условия; честнее фиксировать число расходных категорий или строить график выигрыша от реальной доли повторов.
- Синтетика устроена в духе модели (личный интервал покупки расходника); на реальных данных выигрыш может быть другим.
- Каталог 1500 товаров; одностадийность на реальном каталоге — отдельная задача (см. ниже).

### Потраченные слоты: причина и фикс

**Диагностика** (mid, сид 0, 2000 пользователей): repeat-голова отдаёт уже купленным товарам длительного пользования
лишь 3% своей массы, хотя их 84% среди товаров истории; медиана максимальной массы на такой товар 0.0004 при пороге
попадания в топ ≈ 0.018. **98% потраченных слотов (2458 из 2516) — товары, выпавшие из окна последних 50 покупок**:
модель их не видит, explore-голова не исключает и рекомендует заново. У 92% пользователей история длиннее 50.

**Фикс** (`mask`): explore-голова исключает всю историю пользователя — на обучении (товары до окна каждой
обучающей последовательности) и на инференсе. Определение explore-головы («то, чего не было в истории») теперь
выполняется честно.

### Абляция: 3 режима × 3 сида, Kaggle GPU, тест

Сырые данные: `results/kaggle_ablation/`. Все варианты — против исходного `nn/switch`, парный бутстрап внутри сида.

Recall@10, среднее по 3 сидам; в скобках — в скольких сидах 95% CI разницы с `nn/switch` целиком выше нуля:

| вариант | high | mid | low |
|---------|------|-----|-----|
| `nn/switch` (исходный)  | 0.851 | 0.562 | 0.491 |
| `nn+mask`               | 0.851 (1/3) | **0.613** (3/3) | **0.547** (3/3) |
| `nn+mask+bias`          | 0.848 (0/3) | 0.617 (3/3) | 0.555 (3/3) |
| `nn+mask+null`          | 0.849 (0/3) | 0.615 (3/3) | 0.556 (3/3) |
| `nn+mask+prior`         | 0.850 (1/3) | 0.608 (3/3) | 0.547 (3/3) |
| `nn+mask+all`           | 0.852 (0/3) | 0.613 (3/3) | 0.534 (3/3) |

Средняя разница с `nn/switch`: Recall@10 high +0.001, mid **+0.051**, low **+0.056**; NDCG@10 high +0.001, mid +0.044, low +0.051.

| в среднем по сидам | wasted slots: `nn/switch` → `nn+mask` | Recall explore: `nn/switch` → `nn+mask` | repeat slots |
|--------------------|------------------------|--------------------------|--------------|
| high | 0.062 → 0.013 | 0.133 → 0.161 | 0.79 → 0.76 |
| mid  | **2.03 → 0.008** | 0.313 → **0.394** | 0.51 → 0.31 |
| low  | **2.01 → 0.005** | 0.332 → **0.409** | 0.39 → 0.18 |

Выводы:

- **Маска — весь эффект.** В mid/low она убирает ~2 потраченных слота из 10 (−99.6%) и поднимает Recall@10
  на +0.03…+0.08 во всех 6 прогонах (CI выше нуля). Освободившиеся слоты уходят новым товарам: Recall explore +0.08.
  В high потраченных слотов почти не было — и выигрыша нет.
- **Опции repeat-головы (`bias`, `null`, `prior`) ничего значимого не добавляют.** Разница между `mask+*` — в пределах
  шума. Шум прогон-к-прогону: тот же конфиг `nn/switch` на тех же данных в двух запусках на Kaggle расходится до 0.009 по Recall
  (недетерминизм GPU + ранняя остановка). `null` даёт ровно 0 потраченных слотов, но по Recall равен `mask`.
  По бритве Оккама берём **`mask`** без опций.
- **Главный вывод эксперимента сохраняется и с маской:** `nn+mask/switch` лучше своей же подобранной квоты
  (`nn+mask/fixed-tuned`) во всех 9 прогонах на +0.009…+0.030 и лучше лучшей эвристики (`heur/fixed-tuned`)
  на +0.006…+0.027 в high и +0.08…+0.12 в mid/low. До оракула остаётся 0.007–0.034. (Эти три разницы — по средним, без бутстрапа.)
- **Ранняя остановка шумная:** часть switch-моделей останавливается на 3–5-й эпохе (`patience=3`).
  Это вклад в разброс; `patience` 5 или усреднение по нескольким запускам снизили бы шум.

### Латентность

`latency_bench.py` (веса на задержку не влияют, модели без обучения), режим high, 3074 тестовых пользователя,
300 online-запросов. Плюс тот же замер внутри основного прогона на обученных моделях (Kaggle GPU, 9 прогонов).

| вариант | параметры | batch мс/польз. CPU ноутбука (4 потока) | batch CPU Kaggle (2 потока) | batch GPU Kaggle | online p50 CPU ноутбука | online p50 GPU Kaggle (9 прогонов, ± std) | online p99 GPU Kaggle |
|---------|-----------|------|------|-------|------|-------------|------|
| `freq+pop`     | —       | 0.038 | 0.086 | 0.058 | — | — | — |
| `heur/switch`  | —       | 0.149 | 0.237 | 0.179 | — | — | — |
| `nn/base`      | 203 456 | 0.268 | 0.825 | 0.061 | 1.48 | 2.66 ± 0.08 | 3.20 |
| `nn/switch`    | 209 729 | 0.547 | 2.459 | 0.112 | 2.27 | 3.93 ± 0.09 | 4.52 |
| `nn+mask`      | 209 729 | 0.619 | 2.442 | 0.115 | 2.33 | 4.02 ± 0.11 | 4.97 |
| `nn+mask+all`  | 211 295 | 0.575 | 2.281 | 0.115 | 2.25 | 4.18 ± 0.13 | 5.02 |

- **Фикс по латентности практически бесплатен:** маска +0.09 мс на online p50 на GPU (+2%, на уровне std между прогонами),
  +0.003 мс/польз. в батче; на CPU — в пределах шума. Параметров не добавляет.
- **Цена переключателя (две головы против одной):** ×1.5 по online p50, ×1.8–3 в батче. Она была и раньше.
- **Online на GPU не быстрее, чем на CPU** той же машины Kaggle (p50 `nn/switch` 3.80 против 3.58 мс, `nn/base` 2.57 против 2.50):
  при batch=1 время уходит на Python-обвязку
  и запуск ядер, а не на вычисления. В продакшене это лечится TorchScript/ONNX, батчингом запросов и расчётом голов
  только на последней позиции.
- На батче GPU даёт ×4–22: 0.06–0.12 мс на пользователя.

## Что дальше

1. Стабилизировать режимы: фиксированное число расходных категорий; график выигрыша от реальной доли повторов.
2. Сделать `mask` вариантом по умолчанию; снизить шум ранней остановки (`patience` 5, несколько запусков на конфиг).
3. Взять реальный датасет с повторными покупками (вместо T-ECD) и сравнить с синтетикой.
4. Код под большой каталог: sampled softmax для explore-головы и не плотные (B, L, N) тензоры
   (repeat-голова уже без тензора (B, L, L, d)); на инференсе считать головы только на последней позиции.
5. Вспомогательный BCE-лосс на переключатель (метка «цель — повтор» бесплатна).
6. Новые товары без истории: семантические ID / эмбеддинги описаний.
7. Сравнить с классическим двухстадийным каскадом (кандидаты + бустинг).
